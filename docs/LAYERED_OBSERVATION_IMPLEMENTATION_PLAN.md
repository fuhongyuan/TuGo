## 1. 目标、范围与架构约束

目标：把现有分散的上下文治理、调用可靠性、画板质量检查组织为可组合的分层观察与应对体系。成功调用不代表业务正确；报告未知不能变成通过；结果压缩不能改变执行事实。

本轮包括：统一证据与处理契约、证据持久化和模型视图、工具执行恢复、上下文适配、领域扩展、调度与交付门禁，以及故障注入回归。保留现有画板能力与用户数据。

不包括：完整像素视觉判断、WPS/PowerPoint 外部渲染验证、自动训练/切换模型、第三方插件市场或通用分布式事务。上述能力未检查必须继续明确标注，不能以 DOM 检查替代。

### 1.1 概念与逻辑职责

| 责任单元 | 观察什么 | 可以处理什么 | 禁止 |
| --- | --- | --- | --- |
| Loop 协调 | 上下文预算、模型能力、证据缺失/过期、进展 | 组织模型视图、请求补充观察、交付判断 | 猜测写操作未发生；擅改查询语义 |
| 工具执行器 | 参数、权限、超时、取消、执行回执 | 有预算的安全重试、状态核对、去重 | 无条件重试未知结果的写操作 |
| 领域适配器 | 业务完整性、领域约束、目标效果 | 有授权的分页/汇总及局部修复 | 静默替换用户目标；只读观察产生写入 |
| 环境探针 | 实际数据、文件、DOM/SVG、宿主状态 | 采集带覆盖范围的事实 | 自行决定业务策略或伪造不可用能力 |
| 证据存储与投影 | 事实、处理记录、版本、引用 | 持久化、按权限取回、生成模型视图 | 摘要覆盖原始证据；跨工作区泄露 |

事实、诊断、策略、动作回执、再验证必须可分别追踪。每个问题在同一时刻只有一个自动处理责任方，跨层共享预算，避免重试次数相乘。

### 1.2 对齐现行 Kernel / TuGo Package / Platform 架构

遵守 `docs/architecture/IMPLEMENTATION.md`，不新增第四个产品或独立观察服务：

- Kernel：通用观察契约、Loop 调度、预算和投影策略；通过端口消费工具执行与证据存储。不识别 board/PPT 名称，不依赖 DOM/Electron。
- TuGo Package：画板领域检查、局部修复、效果验收及呈现证据解释。
- Platform：持久化、调用恢复适配、权限、宿主桥接和生命周期；为探针提供能力。
- 执行位置：通用编排在 Node 侧；DOM 探针留在 Renderer，通过宿主边界交换序列化证据；无界面宿主明确返回不支持，而不是使用导出图冒充实时画板。
- 上述为目标边界，不是对当前代码已完成拆分的声明。S1 核实实际目录及端口，优先复用已有拆分，禁止再造一套 Agent Loop。

### 1.3 主要场景

A. 大结果：领域工具产生明细 → 原始结果留存 → Loop 按模型预算取摘要/引用 → 必要时取回明细。
B. 未知写结果：调用超时 → 标记 outcome unknown → 查询回执/状态 → 确认后继续或升级，不直接重放。
C. 画板效果：提交成功 → 等待目标渲染稳定 → 领域检查 → 安全修复或升级 → 对新版本复检。
D. 恢复：进程重启 → 读取执行/证据记录 → 校验当前版本与宿主能力 → 需要时重新观察，不恢复旧通过结论。

## 3. 分步开发与验收

### S1 — 基线与现状核实

交付物：代码/职责映射、现有测试清单、基线结果、待处理缺口；记录 Git HEAD、工作区差异、运行环境与宿主能力。旧的运行日志仅为参考。

重点检查：`runtime-ts/src/{observation,runtime,tools,errors,contextBudget,repository}.ts`、画板观察、CLI/宿主桥接，以及现行三部分拆分是否已经实施。旧 `REACT_OBSERVATION_DESIGN.md` 的“尚未实现”是历史基线，不能据此忽略现有代码，也不能反过来将整篇视为已完成。

测试：运行构建、全量测试、CLI 和 46 节点相关回归，保存逐项退出码。端口/GUI 限制造成的未执行须与功能失败分开。

通过条件：每个已有机制明确归属和证据；确认哪些可复用、哪些要迁移。未通过基线先定位，不能掩盖为新功能完成。

### S2 — 统一证据与策略契约

交付物：版本化、可序列化契约及旧结果适配器；分类不照搬论文全部叶子节点，先覆盖本轮场景并允许扩展。

契约至少分别表达：
- 执行状态（包括结果未知）、证据有效性、检查结论与覆盖范围；
- 结果范围（完整/分页/汇总/部分），原始结果引用和明细入口；
- run/call/attempt/cause、应用/工作区/目标/版本、时间与来源；
- 事实、诊断依据、问题责任方、已执行处理、副作用与再验证关系；
- 工具执行契约：读写、幂等范围/期限、状态查询能力、取消语义、超时语义；未知默认保守；
- 策略动作、权限、前置条件、共享次数/时间/费用预算、升级条件。

测试：正常、失败、未知、未检查、过期、部分结果；非法组合、未知版本、跨边界序列化；旧工具无新字段时的保守降级。

通过条件：类型检查和运行时校验同时通过；不可信工具自报的幂等提示不被当成保证；未知执行状态不能被映射成可直接重试或验收成功。

### S3 — 证据持久化与可逆模型视图

交付物：有界证据存储端口/平台实现；原始结果与模型投影分离；权限、分页、保留期、配额和过期处理。原始证据按安全策略保存，不承诺无限保留。

测试：大结果落盘、分页取回与内容完整性；跨工作区/会话引用拒绝；重启后读取；旧观察不能验收新版本；并发写入、损坏、过期、存储满和清理。敏感凭据不得进入证据或日志，受限数据采用受控引用。

通过条件：摘要不覆写事实；投影可追溯至原始证据；证据不可取回时明确说明而非伪造；存储失败不把已经发生的业务操作说成未发生；旧数据升级/回退路径有测试。

### S4 — 工具执行观察与安全恢复

交付物：执行生命周期观察、错误归类、单一恢复责任方、统一 attempt/预算；适配现有重试、去重与调用账本，禁止叠加第二套隐藏重试。

测试：
1. 明确未执行的暂时失败、安全读请求限流：按预算退避，尊重 Retry-After。
2. 参数/认证/权限错误：不盲目重试，不把策略拒绝当网络波动。
3. 写入成功但响应丢失：通过回执/状态查询核对；副作用计数必须为一次。
4. 无幂等/状态查询保证的未知写结果：升级，不自动重放。
5. 取消、进程崩溃、重启、重复调用 ID、晚到结果：状态一致，不重复应用。
6. 下层内部重试必须计入共享预算；总调用次数不超过配置上限。

通过条件：所有写故障用例副作用符合预期且无重复；取消后不启动新重试；重启不承诺 exactly-once，无法确认时明确返回未知。

### S5 — Loop 的上下文与模型适配

交付物：预算评估、结构化投影、外部引用/按需恢复、历史压缩及能力适配。复用现有 contextBudget/模型能力配置；未授权不自动换模型。

测试：小/大上下文、视觉/纯文本模型、超大多工具结果；预算包含工具定义、历史、图片和输出预留；估算误差有余量。压缩后工具调用/结果配对有效，阻断数量、未知项、原始引用和未完成目标仍保留。

增加对照用例：完整结果和紧凑视图面对同一组可确定问题，答案一致；需要细节时能取回。预算不足以保留最小证据时，明确中止/升级，禁止截成非法 JSON；不为精简而把业务明细变汇总。

通过条件：每次模型调用都有预算和投影记录；能力未知/不支持不冒充已查看图片；无法压缩到安全范围不进入无限压缩循环。测试使用模拟模型，不依赖真实 API 或密钥。

### S6 — 领域适配与本层处理

交付物 A：非绘图查询测试适配器，验证通用核心不依赖 TuGo；测试数据含大结果，支持分页、明确汇总、明细引用。

交付物 B：把现有画板观察注册为领域检查器，把 DOM 检查作为宿主探针；局部修复独立于只读观察。Kernel 不硬编码 board 工具名或几何问题。

测试：
- 查询：完整明细、部分分页、汇总的范围说明正确；明确要求明细时不被静默改成仅汇总；总数未知不编造总数。
- 画板：132 元素/94 条边用例；遮线、文字越界、箭头缺失、不可见描边注入可检出。
- 修复：锁定、空间不足、新增回归、撤销；安全修复再观察，新版本与原报告关联；拒绝候选不计作已应用。
- 探针：播放/编辑未稳定、画板切换、版本竞态/撤销 ABA、字体未就绪、无 UI 宿主；均不虚报通过。

通过条件：同一 Kernel 跑通查询与绘图；观察无写副作用；领域动作不越权；PNG 导出、DOM、像素和外部 PPT 的覆盖范围仍明确区分。

### S7 — 调度、升级与交付

交付物：依据生命周期/风险/变化触发的观察调度，统一去重与预算，结构化升级结果和最终验收。触发规则可配置，保留确定性默认值；不新增无边界的常驻观察循环。

测试：单点低风险编辑、连续批量编辑、未知写结果、环境变化、部分结果、长期无进展、交付前版本变化；多个检查命中同一原因只产生一个处理责任方。模型主动调用和运行时主动调用不重复消费同一观察任务。

故障闭环：观察服务不可用、过期证据、模型忽略阻断、预算耗尽、用户中途修改、取消与重启；通过确定性模拟模型证明证据进入下一轮且不会重放原写操作。

通过条件：无循环重试/修复/压缩；未验证或过期证据不能交付为通过；最终输出说明已完成事实与剩余限制。日志能还原“问题→责任→策略→动作→再验证”。不以模型自报 passed 代替可信证据。

### S8 — 发布门禁与交付

交付物：回归报告、已知限制、回退方式、macOS Apple Silicon 包及哈希；不自动覆盖 /Applications 或真实用户数据。

测试：全量单元/集成、CLI、原生交互、46 节点、安装包内 E2E、包内 CLI 观察与版本失效、发布扫描。用户配置兼容在受控副本/脱敏 fixture 中验证；保留自定义模型/MCP/Skills/提示词/画板及附件，不输出密钥。

性能验收：与 S1 同一硬件/fixture 比较 p50/p95、内存、结果大小、调用数；默认目标无观察路径 p95 回退不超过 10%，超出需说明并处理后复测。超大结果和 46 节点观察设置有界时限/取消点，不允许阻塞 UI 的无限同步扫描。S1 冻结测量方法，阈值调整必须先登记原因，不能事后降低标准掩盖回退。

通过条件：全部门禁有当前构建证据；包内行为与源码一致；未执行门禁不能写“全部通过”；签名/公证状态如实注明。仅在实际达到时把整体状态改为完成。

## 5. 持续更新工作方式

1. 开始工作先读总表和最近记录，只推进依赖满足的步骤；把步骤改为“进行中”。
2. 每个步骤按“补测试→实现→针对性测试→相关回归→记录证据”推进。
3. 代码完成先标“待验收”；逐条通过条件有证据后才改“完成”。失败则修复并保留失败/复测记录。
4. 每个工作批次结束或交接前更新本文；不能只在聊天里说进度。正在运行的测试不是已通过。
5. 阻塞记录具体缺少什么以及可继续的工作，不把未知填通过；范围变更另记，不静默删除验收项。
6. 最终交付以 S8 为准；提交代码不自动代表完成，计划不自动授权发布、推送或修改用户生产数据。

## 7. 研究依据及使用边界

以下支持职责划分与策略，不构成“行业统一四层标准”：
- [Characterizing Faults in Agentic AI](https://arxiv.org/html/2603.06847v2)：故障/症状/原因分类。
- [Model or Harness?](https://arxiv.org/html/2607.28802v1)：交互边界与修复责任。
- [AgentRx](https://arxiv.org/html/2602.02475v2)：执行约束、验证证据和关键失败定位。
- [Diagnosis Before Recovery](https://arxiv.org/html/2608.11772v1)：诊断与干预匹配，不泛化承诺恢复成功率。
- [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 与 [tool design](https://www.anthropic.com/engineering/writing-tools-for-agents)：上下文治理、结果范围与工具返回设计。
- [OpenAI guardrails](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)：Agent/工具边界控制，不等价于完整观察平台。
- [MCP tool annotations](https://modelcontextprotocol.io/specification/2025-06-18/schema#toolannotations)：行为提示不等于可验证执行保证。
