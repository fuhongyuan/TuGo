## 核心目标

产品通过同一套 Agent Kernel SDK，组装功能插件、工具、Skills、提示词和产品壳，低成本形成不同产品形态。

核心区别：不是复制三个 Runtime，也不是仅更换系统提示词，而是让审计、记忆、工具执行等能力通过稳定契约组合。

| 编号 | 架构需求 | 验证方向 |
| --- | --- | --- |
| R1 | Kernel 不理解画板、代码仓库或研究报告 | 移除 Canvas 包后核心仍可测试和运行 |
| R2 | 第一方插件可注册工具、扩展行为和私有状态 | 新增插件不修改核心循环 |
| R3 | Middleware 生命周期、顺序和失败语义明确 | 顺序、超时、异常、取消均有契约测试 |
| R4 | 宿主能力和产品 UI 与核心分离 | Node 无界面场景与 Electron 共用核心 |
| R5 | 安全和副作用不能只依赖提示词 | 未授权执行被拒绝；不确定结果不能盲目重放 |
| R6 | TuGo 既有能力与数据受保护 | 旧数据副本迁移、画板与会话回归通过 |
| R7 | 支持跨产品共享能力，但不默认共享私有数据 | 同一记忆插件可复用，不同产品的数据不串用 |
| R8 | 可观测、可测量，能判断 SDK 是否创造收益 | 追踪、性能和第二场景接入成本有证据 |

## 事实、提案和开放问题

- **现状事实**：来自指定代码基线；代码存在不意味着当前安装包已经通过验收。
- **建议基线**：用于细化设计和技术验证，尚未批准为不可更改的约束。
- **待决策**：存在影响接口、安全或迁移的分歧；在相应实施阶段之前关闭。
- **验收目标**：未来应验证的条件，不是当前已达到的指标。

讨论中的工期是粗估，不是排期承诺；没有把长期恢复、第三方插件隔离或完整 coding/research 产品算作已完成。

## 如何形成可实施定稿

1. 评审原版事实，纠正边界和依赖遗漏。
2. 确认 SDK v0 的范围和不做事项。
3. 用一个非画图场景验证目标接口，而不是先扩张全部能力。
4. 根据实验结果关闭关键决策，补足完整接口、状态转换和迁移规范。
5. 将需求映射到实现任务、测试和回滚办法，形成可实施定稿。

详细阶段与决策编号见 [迁移与验收](03-migration-and-validation.md)。最终设计的完成标准是关键运行语义可测试、任务可拆解、失败可处理，而不只是图和目录齐全。
