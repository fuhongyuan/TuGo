## 1. 可行性与方案选择

| 方案 | 主要收益 | 主要代价 | 当前建议 |
| --- | --- | --- | --- |
| A：继续产品内模块化 | TuGo 交付最快，改造面最小 | 第二产品可能复制基础设施 | 若没有真实第二消费者，仍是合理退路 |
| B：内部 Kernel SDK，第一方静态插件 | 共用运行能力，适度扩展，允许逐步抽离 | 需要维护契约、迁移与跨产品回归 | 建议先以技术验证确认 |
| C：开放插件平台 | 可扩展第三方生态 | 不可信代码隔离、分发、兼容、安全支持显著增加 | 不纳入 SDK v0 |

建议选择 B 的验证阶段，不等于已经批准全部重构。技术可行性有现有 Runtime 基础支持；经济价值需要第二场景接入成本和复用结果证明。

### 1.1 代价与假设

按一名熟悉代码的工程师全职投入估算，保留现有栈、不开发完整新产品 UI：

| 累计目标 | 粗估 | 不包含 |
| --- | --- | --- |
| 验证原型 | 1–2 工程周 | 生产迁移与稳定对外 API |
| 内部 SDK v0、TuGo 接入、最小非画图场景 | 4–8 工程周 | 完整 coding/research 产品 |
| 进一步完成所需审批、恢复、隔离、文档与兼容验证 | 8–16+ 工程周 | 任意第三方插件平台、云多租户 |

这是累计区间，不能逐行相加。完整接口评审和原型之后重新估算。除人力外，还应计入模型测试费用、宿主环境、平台维护、产品延期与发布回归成本；未取得单价与范围前不填写货币预算。

SDK 成本不能全部算成 TuGo 产品改进：导出保真、画板编辑和首次引导仍需要领域投入。平台验证不应成为无限期延后数据安全问题的理由。

## 2. 分阶段迁移

### M0：事实基线与回归准备

- 输入：本文档组与当前代码基线。
- 产物：关键运行行为清单、基线测试记录、开发环境修复方案、迁移数据夹具。
- 工作：核对 Provider 协议、工具调用往返、取消、事件、画板保存、默认配置升级和用户编辑保留。
- 门禁：确认当前哪些测试通过、哪些受环境阻断，不将已有失败归因于重构。
- 回退：只新增测试与文档，不触碰用户数据。

当前已知本机有 Rollup 原生依赖缺失，先核对项目要求的 Node/npm 版本与依赖安装；不得通过删除锁文件或改业务代码掩盖基线环境问题。本次文档工作不执行安装或环境修复。

### M1：5–10 个工作日架构验证

- 输入：固定代码基线，批准的原型范围与有限测试预算。
- 产物：最小注册器、可注入执行路径、Canvas 适配片段、Node 验证宿主、实验报告。
- 场景 A：现有一次“读取画板—修改—返回结果”的闭环通过兼容层运行。
- 场景 B：在隔离测试目录中读取文件、生成补丁，并由测试宿主决定是否应用；不要依赖真实仓库写入或任意 Shell。
- 横切验证：一个只读审计插件在两个场景复用，并带不同领域规则。
- 成功条件：接入 B 主要新增插件/适配，不新增核心产品分支；错误和拒绝行为可观测。
- 止损条件：仍需伪造画板 ID、暴露整个 Repository、改变核心内部状态或复制循环才能接入第二场景。
- 回退：保留有价值的接口和测试，继续方案 A；未通过则不自动进入 M2。

M1 不承诺完整权限系统、长期记忆或生产恢复。只为架构假设提供证据，不能以“演示能跑”宣布 SDK 完成。

### M2：SDK v0 与 TuGo 渐进接入

按依赖推进以下工作包，不要求一次拆完全部目录：

| 工作包 | 主要落点 | 依赖 | 完成证据 |
| --- | --- | --- | --- |
| W1 契约与装配 | `contracts.ts`、`middleware.ts`、候选 Contracts 包 | M1 与 D1/D2 | 注册、冲突、顺序、错误与关闭测试 |
| W2 存储和模型适配 | `repository.ts`、`providers.ts`、候选 Adapter 包 | W1、D5 | 核心不导入 SQL.js 或产品 seed；旧夹具可读 |
| W3 Kernel 抽离 | `runtime.ts`、`runState.ts`、`contextBudget.ts` | W1/W2 | 通用运行、取消、事件与调用记录回归 |
| W4 Canvas 迁出 | `tools.ts`、质量契约、模板、多语言提示词、App bridge | W3、D7 | 核心没有 Canvas/PPT 业务分支 |
| W5 Host 与 facade | `worker.ts`、`runtime-client.cjs`、`src/api.ts` | W3/W4 | 保持 UI 协议的 Electron 测试；Node 无界面运行 |
| W6 双产品验证 | Canvas 与最小非画图能力包 | W5、D8 | 同一核心版本与横切插件复用报告 |

发布门禁：关键决策在 v0 范围内有明确结论、数据兼容与回滚演练通过、原版关键行为未退化。不向 UI 暴露尚未支持的“恢复运行”按钮或任意命令能力。

### M3：按真实需求补齐执行与长任务

只有第二产品确实需要时才推进：持久化审批、执行器取消确认、不确定效果核查、后台长任务、版本固定恢复、资源版本冲突。

先关闭 D3/D4，再开放相关能力。Memory 插件的保留与删除策略、Research 证据模型等也应以真实场景约束，不预先构建泛化知识平台。

### M4：平台化扩张的独立决策

第三方插件、远程 Host、云多租户、热插拔和插件分发需独立威胁模型与收益评估。不能因为内部插件接口已经存在，就自动启用外部代码加载。

## 3. 数据与发布迁移策略

1. 使用脱敏夹具和数据副本；不得直接以唯一用户目录验证迁移，也不自动导入真实凭据。
2. 首批改造保留两个物理数据库；先拆职责与适配接口，不同时合并数据库和改数据模型。
3. 明确一个数据目录只有一个活跃写入实现。新旧 Kernel 可在不同测试目录对比，不能影子运行并同时产生真实副作用。
4. 通过旧 Runtime facade 保持 Renderer IPC 兼容；协议切换与 SDK 内部重构分开验收。
5. 将产品 seed 从通用 open 中迁出时，保留当前用户提示词、模型配置、Skill 编辑、绑定和已有资源 ID；区分系统默认更新与用户自定义内容。
6. Schema 升级先做完整备份；有破坏性变更时先导出再迁移，禁止默认降级覆盖新数据。
7. 回滚先停止运行和写入，再切回已验收实现。若新 Schema 不向后兼容，必须使用明确恢复路径，并说明恢复旧备份会丢失备份后的变更。
8. 产品独立锁定 SDK 版本并验收升级，不强迫所有产品同时发布。

Canvas 工具尚依赖 Renderer 时，SDK 应显式报告宿主能力缺失，而不是在 Node Host 中假装已修改画板。是否将画板权威状态迁出 UI 是 D7，不是抽离核心的隐含前提。

## 4. 副作用与风险登记

| 编号 | 风险 | 影响 | 控制与接受条件 |
| --- | --- | --- | --- |
| K1 | 围绕单产品过度抽象 | 成本增加但复用失败 | M1 必须有真实非画图场景；不需要的扩展点不做 |
| K2 | 迁移导致数据或功能回归 | TuGo 无法可靠使用 | 基线夹具、单写入者、兼容层、恢复演练 |
| K3 | Middleware 顺序或冲突 | 上下文污染、循环、误阻断 | 分阶段贡献、类型化结果、装配校验、仅支持验收组合 |
| K4 | 把接口权限误当沙箱 | 插件或工具越界访问 | 首版可信插件；不可信代码隔离单独立项 |
| K5 | 共享内核扩大故障范围 | 多产品同时退化 | 版本锁定、各产品回归、分批发布 |
| K6 | 额外审计与记忆调用 | 延迟、Token 成本增加 | 最小默认组合、预算与相同任务对照 |
| K7 | 插件升级破坏旧任务 | 恢复失败或行为漂移 | Run 固定装配快照，版本不符时拒绝盲目恢复 |
| K8 | 产品间记忆串用 | 隐私与事实污染 | 产品/工作区命名空间，显式共享授权与删除策略 |
| K9 | 已执行操作被错误重试 | 重复写入或外部副作用 | 调用账本、执行器核查、幂等键；不宣称通用 exactly-once |
| K10 | UI 脱离但工具仍依赖 UI | “后台运行”无效 | 宿主能力声明、健康检查和明确降级；不虚构后台支持 |

接受原则：风险可被测试和约束，且代价与目标产品需求相称才接受。为未来开放生态承担的额外复杂度，不自动计入 v0 必做项。

## 5. 需要深入分析的决策

状态统一为“待评审”。表中的倾向是建议，不是已经批准的 ADR。

| ID | 决策与建议倾向 | 需补的分析或实验 | 关闭时点 |
| --- | --- | --- | --- |
| D1 | 首版静态可信插件，依赖排序与服务槽位显式 | manifest、重复名、依赖环、启动失败清理测试；确认版本策略 | W1 前 |
| D2 | 阶段化 Hook、只读输入、类型化贡献，不共享可变 Checkpoint | 全部阶段顺序、返回类型、错误/取消矩阵、插件冲突案例 | W1 前 |
| D3 | 授权不可绕过，执行器实现可替换 | 威胁模型、路径解析、审批参数绑定、进程/网络边界、失联核查 | 开放真实写文件或命令前 |
| D4 | v0 保留中断语义；持久化恢复单独分期 | 终态与等待状态转换表、恢复算法、未决效果处理、截止时间规则 | W3 前定 v0 边界；M3 前定恢复细节 |
| D5 | 先保留 SQL.js，拆 Port 与产品 seed | StateStore 持久化确认语义、插件状态事务/迁移、双库一致性和回滚 | W2 前 |
| D6 | 统一事件 envelope 与成果引用，领域 payload 有 Schema | 事件游标、重连/去重、非持久化 delta 处理、脱敏、成果授权和回收 | W5 前 |
| D7 | 首版保留 Canvas Renderer bridge，并显式声明限制 | Renderer 当前状态与持久化版本何者权威；并发手工修改；以后是否 headless | W4 前 |
| D8 | 用受控 coding 小场景验证，research 作为后续消费者 | 明确真实任务、允许工具、同一横切插件的复用标准、预算 | M1 开始前 |

每项关闭需记录：背景、备选方案、选定理由、不选理由、约束、测试证据和复议条件。签核角色建议为架构维护者与产品负责人；本文不虚构具体负责人或签核结果。

## 6. 验证矩阵

下表是待执行的验收用例组，不表示已有测试全部覆盖。对比任务使用相同配置和相同输入；真实模型测试需明确费用与数据外发范围，默认先使用模拟模型。

| 组 | 覆盖需求 | 必需用例 |
| --- | --- | --- |
| T1 装配 | R1/R2 | 不装 Canvas 能运行；注册非 board 工具；依赖环、重复工具、独占服务冲突被拒绝 |
| T2 扩展生命周期 | R3/R8 | 确定顺序；Hook 超时/抛错；关闭清理；关键 Hook 失败阻断；观测失败降级可追踪 |
| T3 工具安全 | R5 | 拒绝后零执行；修改授权参数失效；越界路径拒绝；执行器缺失不回退到无限制执行 |
| T4 调用与恢复 | R5/R6 | 重复回包；意图落盘前崩溃；工具已生效但回包丢失；后处理失败不重放；取消与完成竞态 |
| T5 状态与隐私 | R6/R7 | 旧数据与自定义 Skill 保留；插件命名空间隔离；跨产品记忆默认不共享；凭据不进日志 |
| T6 产品兼容 | R4/R6 | TuGo 工具往返、保存/重启、项目切换、取消、快照、导出、Renderer/Worker 丢失 |
| T7 扩展成本 | R1/R2/R8 | 第二场景不复制循环、不伪造项目 ID；共用审计插件；记录新增与修改模块 |
| T8 性能与成本 | R8 | 冷启动、装配耗时、无模型工具延迟、内存、Run 耗时与 Token；与 M0 同环境对照 |

不为尚无测量的指标填造达标数字。M0 记录基线，M1 报告回归幅度；允许阈值由实际使用目标确定，并在 M2 前写入测试门禁。

## 7. 从蓝图到可实施架构设计的完成标准

- [ ] 01 中的原版事实经核对，关键耦合没有遗漏。
- [ ] 确认 SDK v0 范围，明确 Host 信任模型和第一方插件边界。
- [ ] D1–D8 对 v0 所需内容已关闭；延期能力有明确禁用边界，不能以“待定”实现危险默认行为。
- [ ] Contracts 有完整类型、输入/结果 Schema、序列化、异常和兼容规则。
- [ ] Run、工具调用与审批状态机及取消/故障路径有可执行测试。
- [ ] 存储持久化确认、成果生命周期、插件状态迁移和回滚方案明确。
- [ ] 代码依赖边界有自动检查，不依靠开发者口头约定。
- [ ] M1 的双场景证据支持抽象；没有复制循环或重新塞入产品分支。
- [ ] W1–W6 分解为带依赖、范围、验收和负责人的实施任务。
- [ ] 性能/成本门禁、产品回归范围、发布和回滚流程经确认。

满足以上条件后，可将文档升级为“SDK v0 可实施设计 1.0”。这只冻结 v0 范围，不代表开放插件平台或成熟 coding/research 产品已完成。
