# 工具契约与影响反馈：完整设计 v0.1

日期：2026-11-04。状态：**设计提案，供讨论与验证；不是已实现能力清单。**

## 阅读导航

- 先理解问题：第 1～3 节。
- 看系统如何组织：第 4～6 节。

一句话：**让工具执行后的反馈，不只交代“函数返回了什么”，还交代“环境发生了什么变化、凭什么这样判断、哪些仍然不知道”。**

## 1. 设计依据：事实、假设与边界

### 1.1 已有事实

TuGo 的修改可以引发节点变化、连线重新寻路、标签重新定位和实际渲染变化。保存成功并不保证文字、连线和标签的呈现正确。

已定位的案例：连线标签避让遗漏背景容器标题，数据保存成功，但实际产生标题遮挡；旧停止策略又将重复的问题 ID 当作无进展，报成运行服务故障。相关修复与证据见 [观察停滞修复记录](OBSERVATION_STALL_REPAIR.md)。

这些证据支持两点：

1. 操作回执与实际效果之间确实存在信息缺口。
2. 某些缺失信息会影响下一步决策，例如应该局部调整，而不是重放已保存的写入。

### 1.2 待验证假设

**把相关影响组织成结构化反馈，能让 LLM 比只看返回值或临时截图，更可靠、经济地选择下一步。**

这还不是已证明结论。更多反馈也可能带来误报、上下文膨胀和过度修复。因此设计包含对照实验和停止扩展条件，而不是直接要求所有工具迁移。

### 1.3 目标与非目标

目标：减少遗漏重要变化、错误重试、虚假完成和无效修复；让新增工具不再依靠 Agent Loop 中的工具名分支补齐语义。

非目标：不实现万能视觉评分器、不保证图形美观、不自动获得用户授权、不承诺分布式 exactly-once、不建设新消息总线或第二个 Agent Loop、不要求每个工具都截图或调用模型做检查。

本轮仅设计文档，不修改工具行为、数据库格式、用户画板或发布包。

## 2. 术语：避免把不同事情混成“结果”

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| 返回数据 Output | 工具直接提供的业务数据 | 节点 ID、查询记录、导出文件引用 |
| 执行回执 Receipt | 对本次执行已知事实的记录 | 已发送、已确认提交、执行结果未知 |
| 变化 Change | 执行前后状态或派生呈现的差异 | 节点移动、路径改变、标签移位 |
| 影响 Impact | 与调用有关、可能影响决策的变化 | 其他连线被迫绕行、原遮挡消失 |
| 发现 Finding | 某项检查识别的问题 | 标签遮挡标题、文字裁切 |
| 观察 Observation | 具有来源、范围、版本和局限的证据集合 | 当前版本的几何与 DOM 检查 |
| 反馈 Feedback | 从证据投影给 LLM 的决策输入 | 提交成功，但新增一处遮挡，禁止盲目重试 |
| 应对 Treatment | 基于证据采取的动作 | 查回执、重试、修复、停止、请求选择 |

**日志不是观察的替代品，观察也不是自动修复的同义词。**

“副作用”在这里指直接业务结果之外的重要影响，不一定是坏事。为避免与执行安全中的“有状态写入”混淆，统一协议使用 `impacts` 表达连带影响，使用 `effect` 表达读写性质。

## 3. 核心模型：三部分契约，两组公共约束

### 3.1 三部分

| 部分 | 回答的问题 | 必须承担 | 不应承担 |
| --- | --- | --- | --- |
| 声明 Declaration | 工具能做什么、承诺什么？ | 参数/结果规范、能力、限制、权限、失败语义、观察能力 | 把自报能力当作已验证事实 |
| 执行 Execution | 这次实际做了什么？ | 执行、回执、已知变更、错误事实 | 把返回成功解释为效果正确 |
| 观察 Observation | 当前环境变成什么样，依据是什么？ | 收集变化、检查效果、表达范围和未知 | 隐藏写入、私自重试、无限修复 |

异常不是独立第四个顶层部分：错误类型和恢复前提在声明中，异常与副作用事实在执行结果中，对 LLM 的解释在观察中。是否重新行动由恢复控制器决定。

### 3.2 公共约束

- **调用上下文与生命周期**：身份、目标范围、版本、授权、截止时间、取消、后台任务与恢复。
- **平台策略**：工具准入、预算、重试安全、观察调度、证据访问及上下文投影。

这不是要求工具实现五套接口。接入者提供三部分贡献，公共约束由宿主注入和执行。

### 3.3 不变式

1. 成功执行不推出效果通过；没有检查不等于没有问题。
2. 超时不推出没有副作用；取消不推出撤销。
3. 已确认提交的写入，不因观察失败或证据存储失败而重放。
4. 观察默认只读；修复必须成为有身份、授权、预算和回执的新动作。
5. 权限、工作区和调用身份由可信宿主绑定，不从模型参数或工具输出中采信。
6. 一次调用只有一个自动恢复责任方；内部尝试必须消耗同一恢复预算。
7. 反馈可精简，完整问题数量、重要未知和证据引用不得被精简成“通过”。
8. 证据有效性由实际版本、会话和场景身份决定，不由自然语言自称决定。

## 4. 概念架构：谁负责交代什么

```text
                         用户目标与授权
                               │
                               ▼
LLM ──选择动作──▶ 执行控制 ──受控调用──▶ 工具与应用环境
 ▲                    │                       │
 │                    │执行事实               │状态/布局/渲染证据
 │                    ▼                       ▼
 └──决策反馈──── 反馈投影 ◀──证据集合── 观察协调
                     │                    │
                     └──引用──────────────┤
                                          ▼
                                      证据存储
```

声明为执行控制和观察协调提供能力信息，图中省略该静态依赖。

责任分配：

- 工具：最清楚直接执行结果与直接修改。
- 应用领域：最清楚受影响范围、布局重算和领域约束。
- 渲染宿主：最清楚当前画面是否稳定、可见、可测。
- 运行时：负责把这些事实关联起来，并安全、适量地提供给 LLM。
- LLM：依据反馈决定是否改变方案；不得以主观解释覆盖实际证据。

**工具拥有反馈入口，不意味着工具独自生成所有反馈。**

## 5. 逻辑架构：组件、接口与所有权

### 5.1 组件表

| 组件 | 职责与提供接口 | 所需依赖 | 权威状态 |
| --- | --- | --- | --- |
| Tool Registry | 校验和绑定 `RegisteredTool`；提供模型可见描述 | 平台授权/能力目录 | 当前运行固定的注册绑定 |
| Execution Controller | 准入、执行、分类、回执查询与受控重试 | 已绑定工具、账本、恢复策略 | 调用/尝试身份和执行事实 |
| Impact Collector | 采集直接变更、领域派生变化与关联依据 | 工具变更报告、领域差异接口 | 不拥有业务状态，只生成证据 |
| Observation Coordinator | 按范围和版本安排、合并、取消检查 | 观察贡献、调度器、预算 | 待检查范围及检查任务状态 |
| Domain / Host Observers | 提供领域检查和宿主实际呈现证据 | 只读快照或受限探针 | 原始检测事实；不拥有执行终态 |
| Evidence Store | 保存不可变证据、授权取回和过期清理 | 现有 EvidencePort | 证据记录及载荷 |
| Feedback Projector | 生成有预算的 LLM 反馈，保留问题总数和引用 | 回执、证据、上下文预算 | 派生视图，无独立事实源 |
| Delivery Policy | 判断当前声明范围内能否交付 | 当前证据与用户约束 | 验收结论，不改变写入回执 |

以上是逻辑职责，不要求新增八个服务或八个目录。优先复用现有组件，只有变化原因不同、测试边界确实需要时才拆类。

### 5.2 分层所有权

| 层 | 可以决定 | 不能决定 |
| --- | --- | --- |
| Kernel | 通用执行流程、身份、预算、证据协议、反馈载体 | 识别哪条画板线丑、如何调整节点 |
| TuGo Package | 影响闭包、几何/布局语义、质量规则、修复候选 | 自建第二套循环、绕过运行时权限与预算 |
| Platform / Host | 装配、存储、IPC、凭据、能力可信来源、DOM 探针 | 因 MCP 自称幂等就授权未知写入重试 |

业务文档由应用现有存储拥有；执行账本不取代它。观察记录是某个版本的证据，不是新的画板副本数据库。

### 5.3 依赖与安全限制

工具和观察贡献只能接收能力受限的上下文，不接收全量 Repository、密钥、可变 checkpoint 或任意宿主管理接口。观察输出经过 Schema、身份、版本与大小校验后才进入证据存储。

第一方贡献的进程内接口约束不等于恶意代码沙箱。外部 MCP 通过适配器进入同一反馈协议，但其描述、错误分类和“幂等提示”仍是未验证声明，不能获得可信平台恢复权限。

## 6. 契约设计：统一协议，不强制大型继承树

本节 TypeScript 是目标接口草案，用于阐明边界，**不是可直接替换现有代码的补丁**。下面的类型可以组合成对象、函数包装或适配器，不要求所有工具继承一个基类。

### 6.1 声明契约

```ts
type ToolManifest = {
  id: string
  version: string
  contractVersion: 1
  description: string
  inputSchema: JsonSchema
  outputSchema?: JsonSchema
  usage?: { preconditions: string[]; limitations: string[] }
  requires: { permissions: string[]; hostCapabilities: string[] }
  execution: {
    effect: 'read' | 'write' | 'unknown'
    timeoutMs: number
    completion: 'inline' | 'background'
    cancellation: 'before_start' | 'cooperative' | 'unsupported'
    statusQuery: boolean
    idempotency: 'none' | 'keyed' | 'unknown'
  }
  errors: Array<{
    code: string
    category: 'validation' | 'permission' | 'transient'
      | 'rate_limit' | 'conflict' | 'domain' | 'unknown'
  }>
  observation: {
    profile: 'receipt' | 'domain' | 'environment'
    checks: string[]
    supportsImpactScope: boolean
  }
}
```

`JsonSchema` 代表合法 JSON Schema。描述和 usage 为使用提示，不得覆盖用户目标或授权规则。`requires.permissions` 表示所需权限，是否授予仍由宿主判断。

宿主注册时形成单独的 `TrustedBinding`，固定实际 handler、许可的观察器、幂等键作用域/有效期/持久化保证和已审核的执行性质。manifest 不可自我升级为可信绑定。声明 keyed 但缺少有效平台保证，恢复时仍按非幂等处理。

简单旧工具只需提供名称、说明、参数和执行函数；注册包装器补齐保守默认值。默认读写 unknown、无幂等保障、无状态查询、无领域验证；宿主默认超时必须显式记录，不能默认为永久等待。

### 6.2 执行契约

```ts
type ExecutionReceipt<O> = {
  callId: string
  attemptId: string
  outcome: 'not_started' | 'succeeded' | 'failed' | 'unknown'
  commit: 'none' | 'partial' | 'committed' | 'unknown'
  cancellationRequested: boolean
  output?: O
  fault?: {
    code: string
    category: string
    safeMessage: string
    detailRef?: string
  }
  changeRef?: string
  remoteReceiptRef?: string
}
```

语义约束：

- 只读成功为 succeeded + none；确认写入完成为 succeeded + committed。
- 批量非原子操作部分失败，可以是 failed + partial；必须指出已提交范围，不能重新执行整个批次。
- 参数校验拒绝是 not_started + none。
- 已发送写入但丢失响应，缺少可信回执时是 unknown + unknown。
- 请求取消是控制事实；不能抹去已经确认的 succeeded/committed。现有协议中的 cancelled 在迁移适配中保留，不能未经证据映射成 not_started。
- 工具返回了 Promise 或 HTTP 200 不足以确认业务成功；适配器必须处理 `ok:false`、MCP `isError` 及后台任务 ACK。后台 ACK 只确认受理，后续需任务状态/回执。

接口草案：

```ts
interface RegisteredTool<I, O> {
  manifest: ToolManifest
  execute(input: I, context: ExecutionContext): Promise<ToolResponse<O>>
  classifyError?(error: unknown): FaultClassification
  queryStatus?(context: StatusContext): Promise<StatusReceipt<O>>
  observation?: ObservationContribution<I, O>
}
```

这里其余类型的语义是：`ExecutionContext` 提供宿主绑定的身份、目标、预算、取消及受限能力；`ToolResponse` 为业务返回与已知变更报告；`FaultClassification` 为错误类别和已知执行状态；`StatusReceipt` 是经身份核对的回执，不是任意自然语言声明。

正式实现时执行器归一化为 ExecutionReceipt，工具不能伪造 runtime 分配的 callId/attemptId。classifyError 只分类，不调用工具、不睡眠重试；分类器自身失败时降为 unknown。未声明的新异常仍被捕获并保守反馈，不能假设错误列表封闭完备。

执行前的输入 Schema 拒绝，与执行后的输出 Schema 不匹配必须分开。后者可能发生在已经提交之后，应该报告“返回契约不合规、提交事实保持不变”，不能标记为 not_started 并重新写入。执行器保留自己掌握的回执事实，错误分类器不得将其降格为“未执行”。

### 6.3 观察贡献契约

```ts
interface ObservationContribution<I, O> {
  plan(context: Readonly<ObservationPlanningContext<I, O>>): ObservationPlan
  collect(request: Readonly<ObservationRequest>): Promise<ObservationEvidence>
}
```

- plan：根据回执和已知变更，声明所需检查、候选影响范围及预计成本；不能改变业务状态。
- collect：通过白名单只读能力读取指定版本或探针，返回证据；不能自动修图。
- `Readonly` 只是类型约束。真正的写入限制靠不暴露写端口及运行时能力校验。
- 领域工具可引用已有公共观察器，不必重复写 collect；简单工具没有贡献时由平台生成基础执行观察。
- 默认观察仅说明执行事实和输出范围，效果检查为 not_checked，副作用完整性为 unknown；绝不输出“无副作用”作为默认结论。

## 7. 影响反馈的数据模型

### 7.1 内部完整证据与模型反馈分开

完整证据可以包含许多对象和几何数据。LLM 默认只需要与下一步决策有关的摘要，细节按引用查询。

目标反馈包包括：

| 字段组 | 内容 | 来源 |
| --- | --- | --- |
| identity | tool/call/attempt、会话、工作区、版本 | 可信宿主与执行器 |
| execution | 回执状态、提交状态、错误与已执行恢复动作 | 执行账本 |
| output | 业务结果及返回范围 | 工具输出/适配器 |
| changes | 直接修改、间接派生变化、候选受影响对象 | 领域埋点或有界差异分析 |
| impacts | 变化的类型、对象、关联依据、证据引用 | 领域与宿主观察贡献 |
| checks | 检查状态、覆盖范围、版本及局限 | 实际检查器 |
| findings | 新增/消失/仍存在的问题、严重性、对象和度量 | 可比较版本的证据 |
| policy | 是否允许自动重试、可用应对及禁止动作 | 运行时策略 |
| completeness | 完整/摘要/部分、总量、明细引用 | 反馈投影器 |

这不是要求每次塞满所有字段。没有发生的组可以为空；必需语义必须能区分“无相关发现”与“没有检查”。

### 7.2 因果关系不能凭时间顺序编造

每项影响保留 `causes`、目标版本、来源和关联方式：

- `instrumented`：领域执行链明确记录是该调用触发的派生调整。
- `derived`：在隔离或版本核对成立的前后状态中推导出关联。
- `correlated`：仅发现同期变化，无法排除用户/其他任务修改；不能说由该调用导致。

影响证据强度用 reported/measured/unverified 表达，不编造没有校准依据的置信概率。声明“可能受影响”的对象与“已测得发生变化”的对象分开计数。

聚合观察允许关联多个 callId，但不把一个共享渲染结果硬归责给其中某一个调用。缺少前态时只能报告当前发现，不能声称“新产生”或“已经改善”。

发现的 introduced/resolved/persistent 比较要求目标、检查器版本、覆盖范围与度量语义可比较。局部采样没再看见一个范围外的旧问题，不代表它已经 resolved；没有满足条件时使用 transition unknown。

### 7.3 三个相互独立的结论

始终分别表达：

1. **执行结论**：这次动作是否完成、是否产生提交。
2. **观察结论**：在声明覆盖范围内，发现问题/未发现问题/无法判断。
3. **交付结论**：是否满足本次用户请求的验收条件。

几何与 DOM 通过不等于像素通过，更不等于业务语义或审美通过。当前 EvidenceProtocol 的 verdict 继续限制在其声明范围内，不作为万能总分。

## 8. 运行时调度与执行视图

### 8.1 桌面运行位置

```text
本机 Electron 应用
├─ Main 主进程
│  ├─ IPC/能力桥接、RuntimeClient、应用存储适配
│  └─ Node Runtime Worker 线程（独立 JS 执行上下文，不是独立服务）
│     └─ 单一 Agent Loop、工具执行/恢复、观察协调、反馈投影
└─ Renderer 进程
   └─ 画板应用、领域状态/布局、实际 DOM 渲染探针

外部边界：模型服务、MCP 服务；凭据由平台管理。
持久化：沿用现有 App / Runtime 存储及 EvidencePort，不新增第三套业务数据库。
```

位置依据当前 `electron/runtime-client.cjs` 的 Worker 创建及现有宿主桥接。目标组件的精确文件位置待实施时确定。

无界面 Node 宿主仍能执行通用循环和可用工具，但没有挂载的实时画板就只能返回渲染 unavailable/unknown；导出 SVG 不能冒充实际 UI 证据。第一方 Worker 不是不可信扩展沙箱。

### 8.2 一次修改的时序

1. Runtime Worker：绑定工具版本、授权和目标版本；建立 callId。
2. Execution Controller：校验参数/权限/预算，登记调用和本次 attempt，持久化后才能发送执行。
3. Main 桥接：传递绑定身份到 Renderer 的画板适配器。
4. Renderer：按当前应用一致性规则执行修改，返回业务结果与直接变更/已知派生变化。是否“持久化提交”必须以实际保存 ACK 为依据，不能由 UI 显示完成推断。
5. Worker：记录执行回执；Impact Collector 请求有界影响范围；观察协调器安排领域/宿主检查。
6. Renderer：在目标版本、字体/资源就绪、无待提交交互、场景稳定时检查；采样前后再次核对版本/epoch/scene token。
7. Worker：验证与存储证据，生成反馈，再进行下一次 LLM 决策。

检查的等待有截止时间。超时返回“写入成功，渲染待确认”，不能把它变成写入失败。高风险局部修改一般先等一份有界观察再继续；低风险连续调整可以合并检查，但下一次反馈必须带有尚未检查的 dirty 状态。

### 8.3 观察触发

| 触发 | 默认策略 | 目的 |
| --- | --- | --- |
| 普通只读返回 | 基础执行/范围观察，不截图 | 避免无价值开销 |
| 写入影响已知关联对象 | 受影响区域领域检查 | 发现连带调整 |
| 布局高风险或原有 blocker 区域 | 等稳定后实际宿主检查 | 不让后续动作建立在未知呈现上 |
| 连续低风险修改 | 合并同版本/兼容范围检查 | 降低重复采样 |
| 执行异常或未知写结果 | 先记录执行事实，按能力核对回执 | 避免重复副作用 |
| 用户要求完成/导出 | 当前验收范围检查；导出另有目标 | 不以旧 UI 证据替代导出验证 |
| 模型主动要求明细 | 授权读取已有证据，必要时重新观察 | 不把读取当新修复 |

### 8.4 合并、并发、背压与生命周期

- 单一画板写入沿用现有运行互斥和领域版本校验，不宣称能阻止用户手动或所有外部修改。发现并发改变就返回 conflict/stale。
- 检查键至少包含工作区、会话、目标版本、宿主场景身份、检查集、范围和观察器版本。不能仅按工具名去重。
- 同键检查 single-flight；兼容范围可升级并集，但旧调用回执不合并。大范围闭包超预算时必须标记 partial。
- 排队任务设置有界队列，过期版本检查可以取消并安排最新版本；不得静默丢掉全部检查后声称通过。
- 取消一个等待者不取消其他等待者的共享检查；所有等待者离开才取消共享任务。
- 后台任务需要稳定 taskId 与可信状态查询；首批试验不新增后台工具，只预留能力声明。
- 重启后重建未验证范围；已保存证据保留历史意义，旧 Renderer 会话证据不能自动成为当前证据。running/unknown 写入不自动重放。

## 9. 异常、恢复与观察的协作

| 情况 | 执行事实 | 反馈 | 自动应对 |
| --- | --- | --- | --- |
| 参数不合法 | 未开始，无提交 | 字段/约束错误 | 返回 LLM 修正；不是同参重试 |
| 缺少授权 | 未开始，无提交 | 权限不足 | 停止或请求授权，不靠改参数绕过 |
| 只读网络暂时失败 | 无业务写入 | 尝试次数、错误与剩余预算 | 可信只读契约下受控退避 |
| 写入超时，状态未知 | 是否提交未知 | 不确定性和回执能力 | 优先查状态；无保证则不盲重放 |
| 写入确认成功，检测失败 | 已提交，效果未知 | 保留成功与检查错误两项 | 重查观察，不重写 |
| 检测发现新遮挡 | 写入成功，领域问题 | 对象、区域、版本与证据 | 候选局部修复作为新动作 |
| 检查采样时用户修改 | 历史写入事实不变 | 当前证据过期 | 预算内重采，禁止用旧证据交付 |
| 批次部分提交 | 已提交部分可识别 | 已完成与未完成范围 | 只规划剩余部分，禁止整批重放 |
| 观察器崩溃/输出不合规 | 不改变原执行事实 | observation_failed/invalid_evidence | 降级、保留诊断引用，不伪造检查结论 |
| 证据存储失败 | 不改变已确认提交 | 证据无法持久化/取回 | 不承诺可查询；阻止无证据的验收 |

恢复建议是数据，不是恢复授权。调用恢复预算与运行总动作预算共享归责；观察有单独的检查限额和时间预算，但仍受运行总预算限制。不能形成工具重试 × 观察重试 × Agent Loop 重试的无界乘法。

迟到回执追加为历史证据，不再次应用业务修改，不恢复已经取消的 run。已知事实可以通过新证据补充，但已发送的历史反馈不可被静默篡改。

失败信息先脱敏；技术堆栈、原始大响应进入受限明细，不能包含明文凭据。每个模型工具调用必须最终有一个匹配工具结果，即使被策略拒绝或 run 中断。

## 10. 反馈如何进入 ReAct，而不淹没上下文

### 10.1 三档内容，而非每次一份全报告

- **基础档**：执行状态、业务结果范围、是否尚有待检查变化。
- **决策档**：新增 blocker、相关影响、重要未知、已提交范围与禁止重复动作。
- **明细档**：完整对象差异、路径数据、截图、原始回执，通过 EvidencePort 引用按需读取。

优先级：未知提交/部分提交和安全限制 → blocker 与关键证据局限 → 重要影响 → 普通成功细节。输出预算不足时先删普通细节，不删除未知或把问题总数改小。

拟定初始参数，仅用于试验调优：普通反馈约 300～800 tokens；复杂反馈软目标 1,500 tokens；默认展示最多 5 条 finding。安全信息超过软目标时保留最低必要事实，并显式提示遗漏范围及明细引用，不能把软目标当硬截断字符数。

### 10.2 接入模型消息的原则

- 能在同次工具结果返回前完成的检查，放入一次对应工具结果，保持调用/结果配对。
- 延迟检查不为同一个 callId 再伪造第二份 tool result。由已有运行时观察载体传递独立、带身份的补充证据；具体 provider 消息投影由适配器处理。
- 跨轮到达的历史证据，不直接注入另一个工作区或已结束 run；下轮按范围授权读取，并重新判断有效性。
- 工具文字、画板标签及外部网页都是证据数据，不获得系统提示词权力。allowedNext 是平台策略产出的选项；领域字符串不能伪造授权。
- 上下文压缩保留原始用户约束、已提交/未知操作、待验收问题、版本和证据引用；引用过期时重新观察，而不是凭摘要通过。

### 10.3 无进展与停止

只读复查不算修复尝试。相关写入后的新鲜、完整、可比较证据才参与进展判断。问题 ID 相同但遮挡面积下降是进展；缺少度量或版本不一致时不推断“没有改善”。

当前两次相关修复无改善的策略可以继续作为保守上限，而不是新协议硬编码。停止时交代“修改已保存、剩余问题、证据局限”；质量未通过不自动等于服务故障。修改算法保障与反馈协议效果必须分别评估。

## 12. 验证：证明反馈有用，而非仅证明接口能跑

### 12.1 两类测试必须分开

1. **契约正确性**：未知写入不重放、证据不串会话、工具结果不缺配对、观察失败不覆盖写入成功。这些适合确定性测试，属于安全底线。
2. **决策改善**：LLM 是否更少错误行动、更少虚假完成、更少人工介入。这需要固定环境的对照实验，不能由 Schema 测试代替。

### 12.2 三组对照

| 组 | 模型获得的内容 |
| --- | --- |
| A | 现有工具结果与现有明确观察/截图入口，不增加本提案反馈 |
| B | A + 自动提供结构化相关影响及问题/证据局限 |
| C | 基础结构化回执 + 关键主动提示 + 按需查询明细 |

同一模型/版本、提示词、工具与布局算法、初始画板、授权范围、总资源上限。只改变反馈策略。原有布局算法的修复必须对三组同时生效，不能把路由算法收益归到反馈收益上。A 也允许使用原有观察能力，不人为削弱基线。

先做离线轨迹回放检查语义，再做可执行环境中的闭环测试。回放不能替代闭环，因为下一步动作会改变环境。

### 12.3 代表场景

| # | 场景 | 重点 |
| --- | --- | --- |
| 1 | 普通创建，无连带问题 | 是否无谓增加检查/修复 |
| 2 | 移动节点引发多条边改路 | 是否理解间接影响 |
| 3 | 标签遮挡容器标题 | 是否定位并局部处理 |
| 4 | 改文字引发节点扩展及邻近遮挡 | 是否识别跨对象变化 |
| 5 | 写入已提交但响应超时 | 是否避免重复写入 |
| 6 | 参数拒绝与权限拒绝 | 是否区分可修参数与不可绕过权限 |
| 7 | 非原子批次部分成功 | 是否只处理未完成范围 |
| 8 | Renderer 未挂载或尚未稳定 | 是否正确表达未知 |
| 9 | 观察时用户手动修改 | 是否拒绝过期证据 |
| 10 | 连续调整中问题 ID 不变但程度下降 | 是否避免误停 |
| 11 | 大量发现、反馈摘要与明细分页 | 是否保留全量问题计数和关键未知 |
| 12 | UI 正常但导出目标缺线 | 是否避免跨目标错误验收 |

其中部分提交/回执能力等场景可通过明确标记的故障注入宿主实现，只证明协议和模型行为，不代表真实宿主已有该保障。

### 12.4 指标、方法和继续门槛

- 主要指标：最终任务通过率、虚假完成率、重复有副作用操作数。
- 次要指标：无关修改数、修复轮次、人工介入率、token/总费用、端到端延迟、观察自身耗时与误报/漏报。
- Ground truth：确定性结构/几何断言、原生渲染与目标导出检查；表达质量由盲评补充，不由同一模型给自己的解释打分。
- 试运行建议 12 场景 × 5 次独立运行 × 3 组，共 180 次；随机化顺序、保存失败轨迹和版本配置。若服务支持 seed 则记录 seed，否则记录重复实验身份；不假设支持确定性采样。
- 报告配对差异与置信区间。180 次是探索性样本，不保证有统计功效；结果不确定时扩大样本，不能把“没显著差异”直接说成同样有效。

拟定继续门槛，尚未验收：

1. 确定性安全测试中无新增未授权动作、重复提交或虚假通过。
2. 关键故障场景的错误下一步动作率，较 A 相对下降至少 20%；基线为 0 的场景报告绝对差异。
3. 简单场景成功率无有意义退化；反馈不得持续触发额外无关修复。
4. 相同任务集合的中位总 token 增量目标不超过 15%、p95 端到端延迟增量不超过 20%；超出时必须用明确质量收益解释，不能忽略成本。
5. 若 B 不如 C，则保留统一协议与按需策略，不强制富反馈；若两者无可靠收益，只保留必要安全回执和局部专用观察，不扩大通用抽象。

门槛是试验前约定的产品取舍，不是文献结论。置信区间和单场景结果必须同时呈现，不能用平均数掩盖严重退化。

| 步骤 | 交付 | 测试与验收 | 继续条件 |
| --- | --- | --- | --- |
| P0 固定基线 | 真实问题 fixture、任务/资源配置和当前轨迹 | 可重复运行；覆盖正常、异常、连带影响；生产数据只读/脱敏 | 能明确测量缺口 |

| P3 影响与投影 | 因果关联、版本化 payload、引用/摘要/分页 | 同期外部变化不被误归责；总数/引用/未知保真；过期/跨范围引用拒绝 | 反馈可控且可追溯 |
| P4 对照实验 | A/B/C 执行、完整报告和失败分类 | 第 12 节指标；独立效果断言；不删除失败样本 | 证实收益或明确收缩 |
| P5 有条件扩展 | 仅迁移收益明确的工具；能力矩阵和文档 | 全量/兼容性/CLI/画布/原生/导出/打包/审计，旧数据副本验证 | 没有把提案能力冒充实际能力 |

回滚：关闭增强反馈调度/投影，继续使用原执行器、账本和现有观察；新证据保留历史，旧客户端不得把未知新字段解释成成功。配置只可切换反馈策略，不能关闭权限、禁止未知写重放等安全底线。

## 14. 关键决策与待决问题

### 14.0 跨视图追溯

| 设计驱动 | 逻辑机制 | 执行落点 | 验证 |
| --- | --- | --- | --- |
| 执行成功却有连带问题 | Impact Collector + 领域/宿主贡献 | Renderer 测量，Worker 关联与反馈 | 场景 2～4、P2/P4 |
| 未知写入不能重复 | 唯一恢复控制器 + 可信回执契约 | Worker 账本，宿主回执能力 | 场景 5/7、P1/P2 |
| 旧证据不能验收新画面 | 版本/场景身份与覆盖校验 | Renderer 采样前后屏障 | 场景 8/9、P2/P3 |
| 反馈不能淹没模型 | 分档投影 + 明细引用 | Worker 投影与现有 EvidencePort | 场景 11、P3/P4 |
| 协议不是自证有用 | 相同工具算法下的三组对照 | 隔离测试环境，不改生产数据 | P0/P4，收益不明则收缩 |

### 14.1 决策卡

| 决策 | 理由 | 放弃的方案/代价 |
| --- | --- | --- |
| 三部分契约，异常横跨其中 | 区分事实、证据与行动 | 不设包办一切的 onError |
| 统一注册和包装，不统一巨大父类 | 支持本地函数、领域工具、远程 MCP | 少量包装与适配复杂度 |
| 多来源证据由协调器关联 | 工具自己看不到所有渲染/连带变化 | 需要版本与因果元数据 |
| 默认基础反馈，按风险增强 | 避免所有调用都付出截图和检查成本 | 触发策略需要实验校准 |
| 证据不可变、模型反馈可投影 | 兼顾真实性与上下文预算 | 必须管理引用、配额与有效期 |
| 先验证收益再推广 | 区分真实需求与过度抽象 | 不立即统一所有工具 |

### 14.2 尚未决定

1. 哪些影响类型最能改变模型决策？优先通过轨迹标注和 P4 验证，而非先列几百种枚举。
2. 一次局部移动的合适影响范围多大？从关联边/标签及邻近障碍开始，有界扩展；不能预先假定覆盖整个画板。
3. 哪些检查能可靠局部化，哪些必须全局？必须测量遗漏率，未证明之前明确局部覆盖。
4. 业务意图/美观检查何时引入视觉模型？只在确定性证据不足且任务确有需求时独立试验。
5. 什么时候值得给真实画板做可信持久化操作回执？这是执行安全的单独能力建设，不由反馈结构自动提供。

## 15. 学习时可以抓住的主线

这份设计不是“给工具加一个 observe 方法”这么简单，也不是让工具变聪明。

它做的是把一次调用拆成三件独立但可关联的事情：

> **声明承诺什么 → 执行留下什么事实 → 观察获得什么环境证据。**

运行时再把这些内容转成适量反馈，供 LLM 决策。修复仍是下一次受控动作，效果仍要重新观察。

最终是否采用更丰富的反馈，不以接口是否漂亮为依据，而以它是否让模型在相同环境下更少错误行动、且成本可以接受为依据。
